# P1-2 实时消息链路、消息类型与历史恢复

## 任务目标

围绕 Phase1 的统一消息流底座，建立消息历史拉取、WebSocket 实时收发、统一消息模型和前端消息合流能力，为后续 Runtime 与流式输出提供可复用承载层。

## 当前范围

- 消息历史接口：进入会话与刷新页面后的历史恢复
- 会话级 WebSocket 消息通道：连接、断开、会话切换重连
- `send_message`、`ping`、`pong` 三类最小入站动作
- `Message` 基础数据模型与消息类型枚举预留
- 前端消息 store 合并 HTTP 历史与 WS 实时消息

## 不做什么

- 不实现流式 `message_start/message_delta/message_end` 事件，这部分属于 `P1-3`
- 不实现 Runtime 驱动的自动回复、工具调用、任务状态机
- 不实现复杂已读、撤回、编辑、引用回复、附件上传等 IM 增强能力
- 不拆出独立的消息搜索或全文检索能力

## 依赖与前置条件

- 依赖 `P1-1` 已具备会话创建、查询、切换与当前会话恢复能力
- 需要最小用户身份解析和会话访问权限校验能力
- 需要后端可用的 WebSocket 基础设施和消息持久化能力
- 需要前端已有聊天页面与当前会话状态

## 涉及模块

### 后端

- 消息模型与持久化：`Message`
- 历史接口：`GET /api/sessions/{session_id}/messages`
- 实时通道：`WS /ws/{session_id}`
- WebSocket 入站动作解析、权限校验、消息落库与广播

### 前端

- `message store`：历史消息、实时消息、去重与顺序合并
- 会话切换时的 WebSocket 生命周期管理
- 消息列表展示与消息发送表单联动

## 数据模型要求

`Message` 至少包含以下字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 消息唯一标识 |
| `session_id` | string | 是 | 所属会话 |
| `sender_id` | string | 是 | 发送者 ID |
| `role` | enum | 是 | 至少支持 `user`、`assistant`、`system` |
| `type` | enum | 是 | 消息类型 |
| `content` | string | 是 | 主体文本内容 |
| `status` | enum | 是 | 最小状态字段，Phase1 可先支持 `completed` |
| `metadata` | object \| null | 否 | 扩展元信息 |
| `payload` | object \| null | 否 | 结构化内容承载 |
| `created_at` | datetime | 是 | 创建时间 |

`Message.type` 至少预留：

- `text`
- `system`
- `plan`
- `task_status`
- `pending_change`
- `preview`

## 接口契约

### 1. 获取会话消息历史

- 方法：`GET /api/sessions/{session_id}/messages`
- 认证：必需

路径参数：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `session_id` | string | 是 | 会话 ID |

查询参数：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `page` | number | 否 | 页码，默认 `1` |
| `page_size` | number | 否 | 每页条数，默认 `50` |

成功响应：`200 OK`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `items` | Message[] | 按时间顺序返回的消息数组 |
| `page` | number | 当前页 |
| `page_size` | number | 当前分页大小 |
| `total` | number | 总消息数 |

主要错误：

- `401 Unauthorized`：未登录
- `403 Forbidden`：无权访问该会话消息
- `404 Not Found`：会话不存在

### 2. WebSocket 连接

- 路径：`WS /ws/{session_id}`
- 认证：必需，握手时需带当前用户身份

连接校验：

- 当前用户必须对 `session_id` 有访问权限
- 切换会话时必须断开旧连接后再建立新连接

### 3. WebSocket 入站动作

#### `send_message`

请求体：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `action` | string | 是 | 固定为 `send_message` |
| `session_id` | string | 是 | 当前会话 ID |
| `content` | string | 是 | 消息文本 |
| `message_type` | enum | 是 | 当前阶段至少支持 `text` |
| `client_message_id` | string | 是 | 前端本地生成的去重 ID |

服务端处理要求：

- 校验 `session_id` 与当前连接一致
- 校验用户权限
- 生成正式 `Message`
- 写入持久化层
- 将新消息推送回当前会话通道

#### `ping`

请求体：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `action` | string | 是 | 固定为 `ping` |

响应要求：

- 服务端返回 `pong` 或等价心跳响应

#### `pong`

- 允许前端或服务端用于心跳闭环
- 当前阶段只需保证协议兼容，不要求复杂健康探针

### 4. WebSocket 出站消息事件

当前阶段至少支持统一消息推送事件，返回完整 `Message` 对象，字段与历史接口保持一致。

主要错误事件：

- 非法动作
- 非法会话 ID
- 权限不足
- 消息落库失败

错误响应至少包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `type` | string | 错误事件类型 |
| `code` | string | 错误码 |
| `message` | string | 可读错误说明 |

## 详细实现步骤

1. 在后端补齐 `Message` 数据模型、基础索引和与 `Session` 的关联关系。
2. 实现 `GET /api/sessions/{session_id}/messages`，统一走会话权限校验、分页查询与按时间排序返回。
3. 建立会话级 WebSocket 路由 `WS /ws/{session_id}`，实现握手鉴权与会话访问校验。
4. 增加 WebSocket 入站动作解析器，支持 `send_message`、`ping`、`pong` 三类动作。
5. 实现 `send_message` 主链路：参数校验、幂等去重、消息持久化、广播回当前会话连接。
6. 明确统一消息出站结构，使实时推送的 `Message` 与历史接口返回字段一致。
7. 在前端建立 `message store`，统一维护当前会话消息数组、加载状态、分页信息和连接状态。
8. 进入会话时先调用历史接口，再建立 WebSocket 连接；切换会话时关闭旧连接、清理订阅并连接新会话。
9. 把历史消息和实时消息合并到同一数组中，通过 `id` 或 `client_message_id` 去重，确保顺序稳定。
10. 完成发送消息表单联调，验证发送后消息能实时进入当前会话流，刷新后仍可恢复。

## 测试方案

### 后端测试

- 历史接口分页、排序、权限校验正确
- 无权限访问消息历史返回 `403` 或等价错误
- WebSocket 连接对非法会话或越权会话拒绝建连
- `send_message` 能成功落库并广播
- 非法动作、缺失字段、错误 `session_id` 能返回明确错误事件
- 重复 `client_message_id` 不会导致重复消息插入

### 前端测试

- 进入会话先显示历史消息，再接入实时连接
- 发送消息后当前页面能即时展示新消息
- 切换会话时旧连接被清理，新会话消息不会串到旧会话
- 刷新页面后历史消息能恢复，且与实时新消息合并正常
- 不同 `Message.type` 能按统一结构进入消息列表

### 联调验证

- 同一会话多次发送消息时顺序稳定
- 切换不同会话来回发送消息时不会串线
- 历史拉取与实时广播展示一致，不出现双轨状态

## 验收标准

- 用户发送消息后，前端可以实时看到消息进入当前会话流
- 刷新页面后，消息历史可按正确顺序恢复
- `Message` 模型可统一承载多类型消息，而不需要为不同消息形态拆多套结构
- 前端消息状态只维护一套源数据，历史与实时消息不会分裂
- 本 task 不引入流式增量协议和 Runtime 执行逻辑，严格保持在 `P1-2` 边界内
