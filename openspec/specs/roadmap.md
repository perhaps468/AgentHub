# AgentHub 分期重排方案（以 implementation-phases 为准）

---

## 1. 文档定位

本文档用于定义 AgentHub 的阶段边界，是 `proposal.md` 与 `implementation-phases.md` 之间的分层说明文档。

它只解决三件事：

- 每个阶段的目标是什么
- 每个阶段做到什么程度算完成
- 哪些能力应该放在哪一层，不要提前混入下一阶段

后续如果 `roadmap.md` 与 `implementation-phases.md` 有冲突，以 `implementation-phases.md` 为准。

---

## 2. 总体分层原则

- `MVP`：先完成 IM 基础能力、最小聊天闭环与单用户占位，不只是启动壳子
- `P1`：在 MVP 基础上补齐上下文连续、多角色、多 Agent 流水线、最小群聊和 Diff 展示
- `P2`：完成 proposal 的完整基础要求，补齐最小正式 Auth、完整 IM、群聊增强、基础 Orchestrator、多 Provider、自建 Agent、Diff 操作闭环、VFS 接入与部署发布基础版
- `P3`：进入高阶产品化能力，强化高级协同、长期记忆、产物编辑与部署发布增强

统一约束：

- 从 `MVP` 开始保留 `Session`、`Message`、`Agent`、`mode(single/group)`、`content_type` 等核心抽象
- `MVP` 就纳入最小 Session / Message 接口与最小持久化
- `MVP` 与 `P1` 允许暂时使用 `dev_user` 或前端显式 `owner_id` 占位，但要保留后续接入真实用户身份所需的数据边界
- `P2-1` 再纳入最小正式 Auth，把此前临时使用的 `owner_id` 收束为后端 `current_user`
- `P2-1` 验收后，后续阶段不得再依赖 `dev_user` 或前端手传 `owner_id`
- `P1` 才开始真正强调“历史消息作为上下文输入 Agent”
- `P1` 只做固定顺序多 Agent 流水线，不做复杂调度
- `VFS` 是重要能力，但在 `P2` 才正式进入用户可感知闭环

---

## 3. MVP：IM 基础能力、最小聊天闭环与单用户占位

### 3.1 目标

MVP 的目标不是只让前后端跑起来，而是形成一个可以演示、且具备清晰单用户数据边界的最小 IM 系统：

- 前后端能稳定启动
- 有最小聊天页面
- 有按会话工作的 WebSocket
- 有最小 Session / Message 接口
- 有最小会话与消息持久化
- 有 Echo 消息闭环
- 有基础连接状态与重连能力
- 有清晰的 `owner_id` / `dev_user` 数据归属占位方案

### 3.2 范围

- 工程骨架跑通
- 前端最小聊天页跑通
- Session 最小接口可用
- Message 历史接口可用
- `WS /ws/{session_id}` 可用
- 用户消息和 Echo 回复都能持久化
- 刷新页面后可以恢复当前会话消息
- 前端能显示连接状态并支持基础重连
- Session 的 `owner_id` 在 `MVP` 阶段允许由前端显式传入，或由后端挂到固定 `dev_user`
- 数据模型与接口语义要为后续 `P2-1` 收束到 `current_user` 预留空间

### 3.3 MVP 必须具备的接口

- `POST /api/sessions`
- `GET /api/sessions`
- `GET /api/sessions/{session_id}`
- `PATCH /api/sessions/{session_id}`
- `DELETE /api/sessions/{session_id}`
- `GET /api/sessions/{session_id}/messages`
- `WS /ws/{session_id}`

### 3.4 简化策略

- 不接真实 LLM，可先用 Echo Agent
- 不做任务拆解
- 不做多 Agent 协作
- 不做复杂群聊
- 不做 Diff 操作闭环
- 不做正式 VFS 接入
- `MVP` 不做正式 Auth；注册、登录、JWT 和多用户数据隔离后移到 `P2-1`

### 3.5 验收标准

- 前后端都能稳定启动
- 页面能打开并展示最小聊天界面
- 可创建会话、查询会话、进入会话
- 可查询当前会话历史消息
- WebSocket 能按会话实时收发消息
- Echo 回复闭环成立
- 刷新后消息不丢
- 连接状态与基础重连成立
- 基于 `owner_id` / `dev_user` 的单用户链路成立

## 4. P1：多 Agent 最基础产品能力

### 4.1 目标

P1 的目标是在 MVP 基础上，让系统开始像一个“聊天式多 Agent 产品”，而不是只有 IM 壳子。

### 4.2 范围

- 上下文连续与历史恢复增强
- 多角色 Agent 元信息与基础展示
- 固定多 Agent 流水线
- 最小群聊能力
- Diff 产物展示

### 4.3 产品重点

- 历史消息不只用于恢复页面，也要参与 Agent 理解
- 聊天流中出现明确多角色感
- 用户的一条需求能触发最基础的多 Agent 协作
- 群聊开始成立，但只做最小版本
- 系统开始具备结构化产物展示能力

### 4.4 验收标准

- 用户在同一会话连续交互时，Agent 回复能承接前文
- 前端能明确展示 PM、Planner、Coder、Reviewer 等角色
- 固定顺序多 Agent 流水线能跑通
- 至少存在一种最小群聊或 `@Agent` 交互方式
- 聊天流中可稳定展示一类 Diff 或结构化代码产物

---

## 5. P2：proposal 完整基础要求

### 5.1 目标

P2 的目标是完成 proposal 中的完整基础要求，让系统达到“可交作业、可完整讲解、可相对稳定演示”的程度。

### 5.2 范围

- 最小正式 Auth 与用户数据隔离
- 完整 IM 体验
- 群聊增强与参与者管理
- Orchestrator 基础版
- 多 Provider 与自建 Agent
- Diff 操作闭环与 VFS 接入
- 部署发布基础版

### 5.3 产品重点

- 把 `MVP` / `P1` 的临时单用户占位收束为真实账号体系，补齐注册、登录、鉴权与用户数据隔离
- IM 从基础聊天系统升级到更完整的产品体验，包括多会话并行、回复、引用、重新生成、复制代码和展开预览
- 群聊从“最小能力”升级到“可管理能力”
- 多 Agent 协作从固定顺序升级到基础编排
- proposal 中“多 Agent 接入”和“自建 Agent”开始落地
- Diff 从“展示结果”升级到“可操作结果”，支持一键应用 Diff
- VFS 在此阶段正式承担已确认代码状态
- 部署发布先做基础版，覆盖预览 URL、静态部署、源码打包下载和部署状态卡片

### 5.4 验收标准

- 用户可以注册、登录并获取当前用户信息
- 未登录用户不能访问需要身份的 Session、Message 和 WebSocket 能力
- 会话和消息只返回当前登录用户的数据
- 会话置顶、归档、搜索、归档列表查看、多会话并行切换正常
- 回复、引用、重新生成、复制代码和展开预览可用
- 群聊参与者能力可用
- Orchestrator 基础规则可生效
- 至少两个 Provider 可用
- 用户可创建基础 Agent
- Diff Accept / Reject / 一键应用闭环成立
- VFS 能反映已确认代码状态
- 预览 URL、静态部署、源码打包下载和部署状态卡片可用

---

## 6. P3：高阶产品化能力

### 6.1 目标

P3 承接高阶产品化能力和答辩亮点，不再是基础要求层。

### 6.2 范围

- 高级调度与高级群聊
- 长期上下文与记忆
- 产物编辑增强
- 部署发布增强

### 6.3 产品重点

- 强化多 Agent 复杂协同能力
- 强化长周期上下文与长期记忆
- 强化围绕产物本身的持续编辑能力
- 强化从基础发布到容器化、失败反馈和发布记录的完整发布体验

### 6.4 验收标准

- 高级群聊与复杂协作路径可稳定演示
- 长会话上下文承接明显增强
- 产物可围绕局部持续修改
- 产物可进入更完整的容器化部署、发布记录和失败恢复链路

---

## 7. 最终交付验收

最终项目完成时，除产品功能验收外，还必须交付：

- 产品设计文档
- 技术文档
- 可运行 Demo
- AI 协作开发记录
- 3 分钟 Demo 视频

---

## 8. 分阶段实现原则

- 先保证每一层形成独立闭环，再进入下一层
- 当前阶段不提前实现下一阶段能力
- 每一层都应有明确目标、范围和验收标准
- task 拆解应直接依赖 `implementation-phases.md` 的阶段步骤编号
- `roadmap.md` 负责讲“分几步做”，`implementation-phases.md` 负责讲“每一步具体做什么”

---

## 9. 文档关系建议

- `proposal.md`：描述产品愿景与核心能力
- `roadmap.md`：定义 `MVP / P1 / P2 / P3` 阶段边界
- `implementation-phases.md`：定义各阶段的执行步骤与 task 入口

文档职责分工如下：

- `proposal` 负责讲“想做什么”
- `roadmap` 负责讲“分几步做”
- `implementation-phases` 负责讲“每一步做哪些大任务”
