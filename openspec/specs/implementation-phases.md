# AgentHub 分阶段执行版实现文档（MVP / P1 / P2 / P3）

> 本文档是 `roadmap.md` 的执行版母文档。
>
> 它的目标不是把步骤拆得无限细，而是把每个阶段压缩成少量一级任务，同时把“每个任务到底要做什么”写清楚，方便后续继续往下拆具体 task。

---

## 1. 文档定位

本文档用于回答三个问题：

- 当前阶段到底做哪几件大事
- 每件大事的实现范围是什么
- 后续拆更细 task 时，应该从哪里继续拆

本文档的使用方式是：

- 先按阶段看一级任务
- 再在每个一级任务下继续拆二级 task
- 只有当前阶段全部验收通过，才进入下一阶段

## 3. 全局约束

- 从 `MVP` 开始就统一保留 `Session`、`Message`、`Agent`、`mode(single/group)`、`content_type` 这些核心抽象
- `MVP` 先完成 IM 基础能力，所以最小会话接口、最小消息历史接口和最小持久化都放入 `MVP`
- `MVP` 与 `P1` 允许使用 `dev_user` 或显式 `owner_id` 作为单用户占位，但必须保留后续收束到真实用户身份的字段与接口边界
- `P2-1` 补齐最小正式 Auth，把用户身份从临时请求字段收束为后端 `current_user`
- `P2-1` 验收后，后续阶段不得依赖 `dev_user` 或前端手传 `owner_id`
- `P1` 才开始真正强调“上下文连续、多 Agent、群聊雏形、Diff 产物”
- `VFS` 是重要能力，但不是全文主线；在 `P2` 才正式进入用户可感知闭环
- 每个阶段优先做闭环，不优先做功能面

## 4. MVP

### MVP-1 工程骨架跑通

**目标**

让项目能稳定启动，前后端具备独立开发和联调的基础环境。

**要做什么**

- 统一 Monorepo 结构，确保根目录、`frontend`、`backend`、`shared` 的职责清晰
- 整理前后端启动脚本，至少保证本地开发能一键分别启动
- 配置前端代理或后端访问地址，打通前后端基础联调路径
- 明确环境变量最小集合，避免一开始引入过多配置复杂度

**这一阶段产出**

- 可运行的 workspace 配置
- 前端开发服务启动命令
- 后端开发服务启动命令
- 最小 README 或启动说明

**完成标准**

- 执行前端命令后能打开页面
- 执行后端命令后服务能正常监听端口
- 前后端目录结构不再频繁变动

---

### MVP-2 前端最小聊天页跑通

**目标**

先把“能聊天”的前端壳子搭起来，不追求复杂视觉，只追求交互闭环。

**要做什么**

- 搭建最小聊天布局：左侧会话列表区、右侧消息区、底部输入框和发送按钮
- 左侧会话列表先支持最小展示，能显示当前会话和基础会话项
- 右侧消息区要能区分用户消息与 Agent 消息
- 输入框要支持输入、发送、发送后清空
- 页面上要有一个可见的连接状态区域

**前端状态要求**

- 至少要有当前会话状态
- 至少要有消息数组状态
- 至少要有输入框状态
- 至少要有 WebSocket 连接状态

**完成标准**

- 页面能正常渲染
- 输入消息后本地能先显示用户消息
- 收到后端回复后能显示 Agent 消息
- 页面能显示连接状态

---

### MVP-3 Session/Message 最小接口与 WebSocket 跑通

**目标**

MVP 就把 IM 的基础后端骨架立住，不只是一个裸 WebSocket。

**要做什么**

- 提供最小 Session 接口
- 提供最小 Message 历史接口
- 提供按会话维度工作的 WebSocket 端点
- 让前端后续不需要因为接口缺失而推翻 MVP

**MVP 必须具备的接口**

- `POST /api/sessions`
  创建会话，最小字段包括 `owner_id`、`title`、`mode`；`MVP` / `P1` 阶段允许前端显式传入 `owner_id`，或由后端挂到固定 `dev_user`；`P2-1` Auth 完成后必须改为由 `current_user.id` 推导
- `GET /api/sessions`
  查询当前单用户视角下的会话列表，至少支持按更新时间排序；`MVP` / `P1` 阶段允许通过 `owner_id` 过滤或固定 `dev_user`，`P2-1` Auth 完成后“当前用户”必须来自 JWT
- `GET /api/sessions/{session_id}`
  查询单个会话详情
- `PATCH /api/sessions/{session_id}`
  更新会话最小字段，建议至少支持 `title`、`is_pinned`、`is_archived`
- `DELETE /api/sessions/{session_id}`
  删除会话；如果 MVP 不做物理删除，接口也要先保留，允许先返回 `501` 或使用软删除策略，但语义必须定下来
- `GET /api/sessions/{session_id}/messages`
  查询会话消息历史，至少支持 `page`、`page_size`
- `WS /ws/{session_id}`
  当前会话的实时消息通道

**数据要求**

- `Session` 至少要有：`id`、`owner_id`、`title`、`mode`、`created_at`、`updated_at`
- `Message` 至少要有：`id`、`session_id`、`sender_type`、`sender_role`、`content`、`content_type`、`created_at`

**完成标准**

- Session 最小接口可调用
- Message 历史接口可调用
- WebSocket 能按会话连接成功

---

### MVP-4 Echo 消息闭环与最小持久化跑通

**目标**

不仅要“发出去收到回音”，还要把最小会话和消息持久化立住，让 MVP 真正具备 IM 基础能力。

**要做什么**

- 用户发送消息时，前端先本地插入一条用户消息
- 后端接收到消息后，把用户消息写入持久化存储
- 后端生成 Echo 回复，并把 Agent 回复也写入持久化存储
- 后端将 Agent 回复通过 WebSocket 返回给前端
- 前端刷新页面后，重新请求消息历史，能恢复当前会话的消息

**这一阶段的持久化要求**

- `MVP` 就要正式支持会话与消息持久化
- 默认建议直接采用与后续一致的数据存储方案，不要在 MVP 再走一套完全不同的临时模型
- 允许能力简化，但不建议为了“快”完全跳过持久化，否则后面 `P1` 会返工

**最小消息链路**

1. 用户发送消息
2. 用户消息写入消息表
3. 后端生成 Echo 回复
4. Agent 回复写入消息表
5. Agent 回复通过 WebSocket 返回前端
6. 刷新后通过历史接口再次读出两条消息

**完成标准**

- 同一会话内，消息能持续累计
- 刷新页面后历史消息仍在
- 用户消息和 Agent 回复都能查到
- MVP 已具备 IM 最小历史能力

---

### MVP-5 连接状态与基础重连完成

**目标**

把聊天系统最基础的“在线感”和“断线恢复感”补齐。

**本阶段实现决策**

- 不新增 REST 接口，继续复用 `WS /ws/{session_id}`
- 后端最小能力是响应客户端 `{"type": "ping"}` 并返回 `{"type": "pong"}`
- 前端负责连接状态机、客户端心跳、自动重连和失败提示
- 本阶段不统一 WebSocket 消息协议，不把 `shared` 中的理想化流式字段改造成当前后端实际字段，也不反向重构后端消息格式

**要做什么**

- 前端连接成功时显示 `connected`
- 断开时显示 `disconnected`
- 自动重连期间显示 `reconnecting`
- 重连成功后恢复为 `connected`
- 如果重连失败，需要进入 `failed` 状态并给出最小用户提示
- 失败提示中提供手动重试入口，手动重试会重置重连计数并重新连接
- 客户端每 30 秒发送一次 `ping`；如果 `pong` 超时，前端主动关闭当前连接并进入重连流程
- 自动重连采用指数退避：`1s -> 2s -> 4s -> 8s -> 16s`，最多尝试 5 次

**WebSocket 最小行为**

- 连接建立后，前端能感知状态变化
- 客户端心跳使用最小 `ping/pong`
- 服务端只需要保证收到 `ping` 后返回 `pong`；不要求本阶段实现服务端主动心跳
- 不要求此阶段就做复杂降级和轮询兜底
- 不要求此阶段实现离线消息队列、断线期间消息缓存或 HTTP 轮询兜底

**完成标准**

- 断开连接后前端状态能变化
- 自动重连期间前端状态显示为 `reconnecting`
- 重连成功后前端状态恢复为 `connected`
- 连续重连 5 次失败后前端状态进入 `failed`，并显示手动重试入口
- 点击手动重试后，前端能重新进入连接流程
- 重连成功后用户仍能继续发消息

---

### MVP-6 MVP 联调验收

**目标**

确认 MVP 已经是“可演示、可持续联调、单用户链路跑通的最小 IM 系统”，而不是只完成了若干分散功能。

**联调要覆盖的场景**

- 启动前端与后端
- 创建会话
- 查询会话列表
- 进入某个会话
- 发送消息
- 收到 Echo 回复
- 刷新页面后恢复历史消息
- 模拟 WebSocket 断开并观察重连
- 使用同一 `owner_id` / 固定 `dev_user` 持续完成单用户聊天链路

**MVP 最终验收标准**

- 前后端都能稳定启动
- 基于 `owner_id` / 固定 `dev_user` 的单用户链路成立
- 会话最小接口可用
- 消息历史接口可用
- WebSocket 可按会话实时收发消息
- Echo 回复闭环成立
- 刷新后消息不丢
- 连接状态与基础重连成立

## 5. P1

### P1-1 上下文连续与历史恢复增强

**目标**

让系统从“有历史”升级为“历史真正参与 Agent 理解”。

**要做什么**

- 在 Agent 响应前读取当前会话历史消息
- 统一会话上下文注入逻辑，不能每个 Agent 各自随便拼接
- 历史恢复不再只是 UI 展示，而是成为后端推理输入的一部分
- 支持基础多轮交互：用户补充一句后，Agent 能接着上文继续说

**完成标准**

- 用户在同一会话连续提问，Agent 的回复明显依赖前文
- 历史消息既用于前端恢复，也用于后端上下文输入

---

### P1-2 多角色 Agent 元信息与基础展示

**目标**

让聊天流里出现明确的多角色感，而不是只有一个模糊的“机器人”。

**要做什么**

- 定义 PM、Planner、Coder、Reviewer 等固定角色
- 每个角色至少有 `name`、`role`、`avatar` 占位、`system_prompt` 基础信息
- 前端消息气泡要能展示不同角色身份
- typing 状态要能带角色名出现

**完成标准**

- 前端可以清楚区分不同 Agent 的消息身份
- 后端可以按角色组织后续流水线

---

### P1-3 固定多 Agent 流水线

**目标**

先实现最基础的多 Agent 协作感，不做复杂调度。

**要做什么**

- 用户发送需求后，按固定顺序进入多 Agent 处理
- 建议最小顺序为：`PM -> Planner -> Coder -> Reviewer`
- PM 负责澄清或总结需求
- Planner 负责输出结构化任务方向
- Coder 负责输出最小代码结果或 Diff 结果
- Reviewer 负责给出通过/修改建议

**约束**

- 这一阶段不做动态分派
- 不做并行协作
- 不做复杂冲突处理

**完成标准**

- 一条用户消息能触发一轮固定多 Agent 协作
- 多角色回复顺序清晰，前端能正确展示

---

### P1-4 最小群聊能力

**目标**

让 proposal 里的“群聊”开始成立，但只做最小版本。

**要做什么**

- 数据模型保留 `mode=group`
- 会话可标记为群聊
- 消息协议支持 `mentioned_agents`
- 用户可以在消息中显式 `@某个 Agent`
- 被提及的 Agent 或固定顺序 Agent 响应

**这一阶段不做什么**

- 不做复杂参与者管理界面
- 不做多 Agent 自主讨论
- 不做并行消息流

**完成标准**

- 至少存在一种最小群聊交互方式
- 用户能感知“这是一个不止单角色回复的会话”

---

### P1-5 Diff 产物展示

**目标**

让系统从聊天工具升级为“能在聊天里展示产物”的产品雏形。

**要做什么**

- Coder 输出结构化代码结果
- 前端把结果显示成 Diff 卡片、结构化代码块或等价形式
- Reviewer 可围绕该产物给出审查意见
- 聊天流中不仅有文本，也出现第一类结构化产物

**约束**

- 这一阶段只要求“展示”
- 不要求用户已经能 Accept / Reject 并更新文件状态

**完成标准**

- 聊天流中可稳定出现一类结构化代码产物
- 用户能看懂这是“待确认的代码结果”，不是纯文字回复

---

### P1-6 P1 联调验收

**联调要覆盖的场景**

- 进入已有会话，加载历史消息
- 连续多轮发消息，观察上下文承接效果
- 触发固定多 Agent 流水线
- 在群聊或 `@Agent` 场景下观察最小群聊能力
- 查看 Diff 产物展示

**P1 最终验收标准**

- 上下文连续成立
- 多角色展示成立
- 固定多 Agent 流水线成立
- 最小群聊能力成立
- 至少一种结构化产物展示成立

## 6. P2

### P2-1 Auth 最小正式闭环与用户隔离

**目标**

把 `MVP` / `P1` 的临时用户标识收束为正式账号身份，让会话和消息在进入完整产品化前具备可靠的数据归属边界。

**要做什么**

- 新增最小 `User` 数据模型
- 支持邮箱密码注册
- 注册和登录都必须使用密码哈希，不能保存明文密码
- 登录成功后签发 JWT
- 提供获取当前用户信息的接口
- REST 接口通过 `Authorization` 解析 `current_user`
- WebSocket 建连时通过 JWT 识别当前用户
- 创建 Session 时，`owner_id` 由 `current_user.id` 写入，不再由前端传入
- 查询 Session 和 Message 时，只能访问当前用户拥有的会话和消息
- 前端补齐最小登录态：未登录进入登录/注册入口，登录后进入聊天页，刷新后能恢复登录态

**P2 必须具备的 Auth 接口**

- `POST /api/auth/register`
  使用邮箱、密码和可选昵称创建用户。
- `POST /api/auth/login`
  校验邮箱密码，返回 JWT 和当前用户基础信息。
- `GET /api/auth/me`
  基于 JWT 返回当前用户基础信息。

**数据要求**

- `User` 至少要有：`id`、`email`、`password_hash`、`display_name`、`created_at`、`updated_at`
- `email` 必须唯一
- `Session.owner_id` 必须指向真实用户 ID
- `Message` 继续通过 `session_id` 归属于会话，不额外引入复杂权限模型

**这一阶段不做什么**

- 不做邮箱验证
- 不做找回密码
- 不做 OAuth 或第三方登录
- 不做 Refresh Token 或 Token 轮换机制
- 不做复杂角色权限系统
- 不做管理后台
- 不做组织、多租户或团队空间

**完成标准**

- 用户可以注册、登录并获取当前用户信息
- 密码以哈希形式保存
- 未登录用户不能访问需要身份的 Session、Message 和 WebSocket 能力
- 创建会话时前端不再传 `owner_id`
- 会话列表只返回当前登录用户的数据
- 消息历史和 WebSocket 只允许访问当前登录用户拥有的会话
- 两个不同用户之间的会话和消息互不可见

---

### P2-2 完整 IM 体验

**目标**

把聊天产品该有的基础体验补齐。

**要做什么**

- 会话置顶
- 会话归档
- 会话搜索
- 归档列表查看与恢复
- 多会话并行切换与状态保持
- 回复消息
- 引用消息
- 重新生成
- 复制代码
- 展开预览
- 更平滑的历史分页加载

**完成标准**

- 系统已不只是“能聊天”，而是具备基础 IM 产品体验
- 用户可以在多个会话之间切换，并保持各自历史、状态和任务上下文
- 回复、引用、重新生成、复制代码和展开预览等基础消息操作可用

---

### P2-3 群聊增强与参与者管理

**目标**

让群聊从“最小能力”升级为“可管理的能力”。

**要做什么**

- 引入群聊参与者记录
- 支持群聊中的 Agent 列表展示
- 支持会话级参与者管理
- 让多个 Agent 能在同一会话中更稳定协作

**完成标准**

- 群聊不再只是消息协议占位，而是真正具备参与者概念

---

### P2-4 Orchestrator 基础版

**目标**

从固定顺序流水线升级到基础编排。

**要做什么**

- 根据用户输入决定唤起哪些 Agent
- 决定基础回复顺序
- 聚合多个 Agent 产出
- 保留规则驱动实现，不追求智能调度复杂度

**完成标准**

- 系统不再只能跑死板固定链路
- 已具备基础“主 Agent 协调”能力

---

### P2-5 多 Provider 与自建 Agent

**目标**

让 proposal 里的“多 Agent 接入”和“用户自建 Agent”开始落地。

**要做什么**

- 抽象统一 Provider 适配器接口
- 至少接入两个 Provider
- 支持创建基础自定义 Agent
- 支持配置名称、角色、Prompt、模型、能力标签

**完成标准**

- 同一系统内至少有两个 Provider 可用
- 用户可新增基础 Agent，而不只是使用内置角色

---

### P2-6 Diff 操作闭环与 VFS 接入

**目标**

让 Diff 从“展示结果”变成“可操作结果”，并在这个阶段正式接入 VFS。

**要做什么**

- 支持用户 Accept Diff
- 支持用户 Reject Diff
- 支持用户一键应用 Diff
- Reject 后重新生成
- Accept 后更新正式项目文件状态
- 引入正式 VFS 承载已确认代码状态
- 必要时把确认后的文件状态同步到磁盘或预览环境

**约束**

- `VFS` 在这里是重要能力，但它服务于“Diff 操作闭环”，不是单独成章自转

**完成标准**

- 用户对 Diff 的操作能真实改变项目状态
- `VFS` 能反映已确认结果

---

### P2-7 部署发布基础版

**目标**

让 proposal 中的部署发布能力先具备可演示的基础版，而不是全部推迟到高阶阶段。

**要做什么**

- 生成预览 URL
- 支持静态部署
- 支持源码打包下载
- 在聊天流中展示部署状态卡片

**这一阶段不做什么**

- 不做容器化部署
- 不做复杂发布回滚
- 不做完整部署失败恢复
- 不做多环境发布管理

**完成标准**

- 用户可以从聊天流看到部署状态
- 至少一种静态预览或静态部署路径可用
- 用户可以下载源码包

---

### P2-8 P2 联调验收

**联调要覆盖的场景**

- 注册用户
- 登录用户
- 刷新页面后恢复登录态
- 会话搜索、置顶、归档、多会话并行切换

- `VFS` 更新结果可感知
- 预览 URL、静态部署、源码打包下载和部署状态卡片

**P2 最终验收标准**

- Auth 最小正式闭环成立

## 8. 如何从本文档继续拆 task

后续建议按下面的方式继续拆：

- 一级 task：直接使用本文档的步骤编号，如 `MVP-1`、`MVP-2`、`P1-3`
- 二级 task：从“要做什么”里继续拆成接口、前端、后端、联调四类子任务

例如：

- `MVP-3-1` 定义 Session 数据模型
- `MVP-3-2` 实现 `POST /api/sessions`
- `MVP-3-3` 实现 `GET /api/sessions`
- `MVP-3-4` 实现 `GET /api/sessions/{id}`
- `MVP-3-5` 实现 `GET /api/sessions/{id}/messages`
- `MVP-4-1` 用户消息持久化
- `MVP-4-2` Echo 回复持久化
- `MVP-4-3` 刷新后消息恢复

这样拆下去会比从超细总设计里拆自然很多。
