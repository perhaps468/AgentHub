# AgentHub 分阶段执行版实现文档（MVP / P1 / P2 / P3）

> 本文档是 `roadmap.md` 的执行版母文档。
>
> 它的目标不是把步骤拆得无限细，而是把每个阶段压缩成少量一级任务，同时把“每个任务到底要做什么”写清楚，方便后续继续往下拆具体 task。

---

## 1. 文档定位

本文档用于回答三个问题：

- 当前阶段到底做哪几件大事
- 每件大事的实现范围是什么
- 后续拆更细 task 时，应该从哪里继续拆

本文档的使用方式是：

- 先按阶段看一级任务
- 再在每个一级任务下继续拆二级 task
- 只有当前阶段全部验收通过，才进入下一阶段

## 3. 全局约束

- 从 `MVP` 开始就统一保留 `Session`、`Message`、`Agent`、`mode(single/group)`、`content_type` 这些核心抽象
- `MVP` 先完成 IM 基础能力，所以最小会话接口、最小消息历史接口和最小持久化都放入 `MVP`
- `MVP` 与 `P1` 允许使用 `dev_user` 或显式 `owner_id` 作为单用户占位，但必须保留后续收束到真实用户身份的字段与接口边界
- `P2-1` 补齐最小正式 Auth，把用户身份从临时请求字段收束为后端 `current_user`
- `P2-1` 验收后，后续阶段不得依赖 `dev_user` 或前端手传 `owner_id`
- `P1` 先验证真实单 Agent、句段级流式和最小上下文承接，不提前引入多 Agent 协作主线
- `P2` 才进入多角色、多 Agent 协作、群聊和 Diff 展示，并在真实用户边界下建立平台基础能力
- `P2` 不做自建 Agent、Diff/VFS 正式闭环和部署发布
- `P3` 才补齐自建 Agent、Diff/VFS 正式闭环与完整部署，并承接高级调度、长期记忆和产物编辑增强
- 每个阶段优先做闭环，不优先做功能面

## 4. MVP

### MVP-1 工程骨架跑通

**目标**

让项目能稳定启动，前后端具备独立开发和联调的基础环境。

**要做什么**

- 统一 Monorepo 结构，确保根目录、`frontend`、`backend`、`shared` 的职责清晰
- 整理前后端启动脚本，至少保证本地开发能一键分别启动
- 配置前端代理或后端访问地址，打通前后端基础联调路径
- 明确环境变量最小集合，避免一开始引入过多配置复杂度

**这一阶段产出**

- 可运行的 workspace 配置
- 前端开发服务启动命令
- 后端开发服务启动命令
- 最小 README 或启动说明

**完成标准**

- 执行前端命令后能打开页面
- 执行后端命令后服务能正常监听端口
- 前后端目录结构不再频繁变动

---

### MVP-2 前端最小聊天页跑通

**目标**

先把“能聊天”的前端壳子搭起来，不追求复杂视觉，只追求交互闭环。

**要做什么**

- 搭建最小聊天布局：左侧会话列表区、右侧消息区、底部输入框和发送按钮
- 左侧会话列表先支持最小展示，能显示当前会话和基础会话项
- 右侧消息区要能区分用户消息与 Agent 消息
- 输入框要支持输入、发送、发送后清空
- 页面上要有一个可见的连接状态区域

**前端状态要求**

- 至少要有当前会话状态
- 至少要有消息数组状态
- 至少要有输入框状态
- 至少要有 WebSocket 连接状态

**完成标准**

- 页面能正常渲染
- 输入消息后本地能先显示用户消息
- 收到后端回复后能显示 Agent 消息
- 页面能显示连接状态

---

### MVP-3 Session/Message 最小接口与 WebSocket 跑通

**目标**

MVP 就把 IM 的基础后端骨架立住，不只是一个裸 WebSocket。

**要做什么**

- 提供最小 Session 接口
- 提供最小 Message 历史接口
- 提供按会话维度工作的 WebSocket 端点
- 让前端后续不需要因为接口缺失而推翻 MVP

**MVP 必须具备的接口**

- `POST /api/sessions`
  创建会话，最小字段包括 `owner_id`、`title`、`mode`；`MVP` / `P1` 阶段允许前端显式传入 `owner_id`，或由后端挂到固定 `dev_user`；`P2-1` Auth 完成后必须改为由 `current_user.id` 推导
- `GET /api/sessions`
  查询当前单用户视角下的会话列表，至少支持按更新时间排序；`MVP` / `P1` 阶段允许通过 `owner_id` 过滤或固定 `dev_user`，`P2-1` Auth 完成后“当前用户”必须来自 JWT
- `GET /api/sessions/{session_id}`
  查询单个会话详情
- `PATCH /api/sessions/{session_id}`
  更新会话最小字段，建议至少支持 `title`、`is_pinned`、`is_archived`
- `DELETE /api/sessions/{session_id}`
  删除会话；如果 MVP 不做物理删除，接口也要先保留，允许先返回 `501` 或使用软删除策略，但语义必须定下来
- `GET /api/sessions/{session_id}/messages`
  查询会话消息历史，至少支持 `page`、`page_size`
- `WS /ws/{session_id}`
  当前会话的实时消息通道

**数据要求**

- `Session` 至少要有：`id`、`owner_id`、`title`、`mode`、`created_at`、`updated_at`
- `Message` 至少要有：`id`、`session_id`、`sender_type`、`sender_role`、`content`、`content_type`、`created_at`

**完成标准**

- Session 最小接口可调用
- Message 历史接口可调用
- WebSocket 能按会话连接成功

---

### MVP-4 Echo 消息闭环与最小持久化跑通

**目标**

不仅要“发出去收到回音”，还要把最小会话和消息持久化立住，让 MVP 真正具备 IM 基础能力。

**要做什么**

- 用户发送消息时，前端先本地插入一条用户消息
- 后端接收到消息后，把用户消息写入持久化存储
- 后端生成 Echo 回复，并把 Agent 回复也写入持久化存储
- 后端将 Agent 回复通过 WebSocket 返回给前端
- 前端刷新页面后，重新请求消息历史，能恢复当前会话的消息

**这一阶段的持久化要求**

- `MVP` 就要正式支持会话与消息持久化
- 默认建议直接采用与后续一致的数据存储方案，不要在 MVP 再走一套完全不同的临时模型
- 允许能力简化，但不建议为了“快”完全跳过持久化，否则后面 `P1` 会返工

**最小消息链路**

1. 用户发送消息
2. 用户消息写入消息表
3. 后端生成 Echo 回复
4. Agent 回复写入消息表
5. Agent 回复通过 WebSocket 返回前端
6. 刷新后通过历史接口再次读出两条消息

**完成标准**

- 同一会话内，消息能持续累计
- 刷新页面后历史消息仍在
- 用户消息和 Agent 回复都能查到
- MVP 已具备 IM 最小历史能力

---

### MVP-5 连接状态与基础重连完成

**目标**

把聊天系统最基础的“在线感”和“断线恢复感”补齐。

**本阶段实现决策**

- 不新增 REST 接口，继续复用 `WS /ws/{session_id}`
- 后端最小能力是响应客户端 `{"type": "ping"}` 并返回 `{"type": "pong"}`
- 前端负责连接状态机、客户端心跳、自动重连和失败提示
- 本阶段不统一 WebSocket 消息协议，不把 `shared` 中的理想化流式字段改造成当前后端实际字段，也不反向重构后端消息格式

**要做什么**

- 前端连接成功时显示 `connected`
- 断开时显示 `disconnected`
- 自动重连期间显示 `reconnecting`
- 重连成功后恢复为 `connected`
- 如果重连失败，需要进入 `failed` 状态并给出最小用户提示
- 失败提示中提供手动重试入口，手动重试会重置重连计数并重新连接
- 客户端每 30 秒发送一次 `ping`；如果 `pong` 超时，前端主动关闭当前连接并进入重连流程
- 自动重连采用指数退避：`1s -> 2s -> 4s -> 8s -> 16s`，最多尝试 5 次

**WebSocket 最小行为**

- 连接建立后，前端能感知状态变化
- 客户端心跳使用最小 `ping/pong`
- 服务端只需要保证收到 `ping` 后返回 `pong`；不要求本阶段实现服务端主动心跳
- 不要求此阶段就做复杂降级和轮询兜底
- 不要求此阶段实现离线消息队列、断线期间消息缓存或 HTTP 轮询兜底

**完成标准**

- 断开连接后前端状态能变化
- 自动重连期间前端状态显示为 `reconnecting`
- 重连成功后前端状态恢复为 `connected`
- 连续重连 5 次失败后前端状态进入 `failed`，并显示手动重试入口
- 点击手动重试后，前端能重新进入连接流程
- 重连成功后用户仍能继续发消息

---

### MVP-6 MVP 联调验收

**目标**

确认 MVP 已经是“可演示、可持续联调、单用户链路跑通的最小 IM 系统”，而不是只完成了若干分散功能。

**联调要覆盖的场景**

- 启动前端与后端
- 创建会话
- 查询会话列表
- 进入某个会话
- 发送消息
- 收到 Echo 回复
- 刷新页面后恢复历史消息
- 模拟 WebSocket 断开并观察重连
- 使用同一 `owner_id` / 固定 `dev_user` 持续完成单用户聊天链路

**MVP 最终验收标准**

- 前后端都能稳定启动
- 基于 `owner_id` / 固定 `dev_user` 的单用户链路成立
- 会话最小接口可用
- 消息历史接口可用
- WebSocket 可按会话实时收发消息
- Echo 回复闭环成立
- 刷新后消息不丢
- 连接状态与基础重连成立

## 5. P1

### P1-1 单 Provider 薄适配与首个真实 Agent 接入

**目标**

让系统从 Echo 壳子升级为真实单 Agent 产品，但不提前引入多 Provider 平台复杂度。

**要做什么**

- 接入一个真实 Agent Provider
- 保留足够薄的 Provider 接口，为 `P2` 的多 Provider 接入预留空间
- 默认只提供一个真实 Agent 入口，不要求会话内切换 Agent
- 前端能明确展示当前唯一真实 Agent 的身份

**约束**

- 不在本阶段实现至少两个 Provider
- 不在本阶段实现用户自建 Agent
- 不在本阶段搭建完整多角色体系

**完成标准**

- 用户进入系统后可以稳定与默认唯一真实 Agent 对话
- Provider 接入不是硬编码死在业务流程里，后续可扩展到多 Provider

---

### P1-2 句段级流式输出与 `typing`

**目标**

让真实 Agent 回复具备清晰的实时感，同时控制协议和实现复杂度。

**要做什么**

- 将真实 Agent 输出以句段级 chunk 推送到前端
- 前端支持按 chunk 追加消息内容
- 增加最小 `typing` 状态展示
- 保持当前消息协议和共享抽象的方向一致，不强行提升到逐 token

**约束**

- 流式粒度只做到句段级 chunk
- 不要求逐 token 流式
- 不要求本阶段支持复杂中断、续传或消息合并策略

**完成标准**

- 聊天流中可稳定看到句段级流式内容追加
- 前端在 Agent 输出期间可展示 `typing` 状态

---

### P1-3 最小上下文承接

**目标**

让真实 Agent 从“单轮应答”升级为“能承接最近历史的连续对话”。

**要做什么**

- 在 Agent 响应前读取当前会话近历史消息
- 统一近历史注入逻辑，避免后续每个 Agent 各自拼接
- 支持基础多轮交互：用户补充一句后，Agent 能接着上文继续说

**约束**

- 只承接当前会话近历史
- 不做 pin、摘要、长期记忆或跨会话上下文
- 不把“历史恢复增强”扩展成这一阶段的独立重能力

**完成标准**

- 用户在同一会话连续提问时，真实 Agent 的回复能承接最近前文
- 历史消息既用于前端恢复，也用于最小后端上下文输入

---

### P1-4 P1 联调验收

**联调要覆盖的场景**

- 进入已有会话，加载历史消息
- 与默认唯一真实 Agent 连续多轮对话
- 观察句段级流式输出
- 观察 `typing` 状态和流式渲染
- 观察近历史承接效果

**P1 最终验收标准**

- 真实单 Agent 链路成立
- 句段级流式输出成立
- `typing` 状态成立
- 最近历史承接成立

## 6. P2

### P2-1 Auth 最小正式闭环与用户隔离

**目标**

把 `MVP` / `P1` 的临时用户标识收束为正式账号身份，让会话和消息在进入多 Agent 协作前具备可靠的数据归属边界。

**要做什么**

- 新增最小 `User` 数据模型
- 支持邮箱密码注册
- 注册和登录都必须使用密码哈希，不能保存明文密码
- 登录成功后签发 JWT
- 提供获取当前用户信息的接口
- REST 接口通过 `Authorization` 解析 `current_user`
- WebSocket 建连时通过 JWT 识别当前用户
- 创建 Session 时，`owner_id` 由 `current_user.id` 写入，不再由前端传入
- 查询 Session 和 Message 时，只能访问当前用户拥有的会话和消息
- 前端补齐最小登录态：未登录进入登录/注册入口，登录后进入聊天页，刷新后能恢复登录态

**P2 必须具备的 Auth 接口**

- `POST /api/auth/register`
  使用邮箱、密码和可选昵称创建用户。
- `POST /api/auth/login`
  校验邮箱密码，返回 JWT 和当前用户基础信息。
- `GET /api/auth/me`
  基于 JWT 返回当前用户基础信息。

**数据要求**

- `User` 至少要有：`id`、`email`、`password_hash`、`display_name`、`created_at`、`updated_at`
- `email` 必须唯一
- `Session.owner_id` 必须指向真实用户 ID
- `Message` 继续通过 `session_id` 归属于会话，不额外引入复杂权限模型

**这一阶段不做什么**

- 不做邮箱验证
- 不做找回密码
- 不做 OAuth 或第三方登录
- 不做 Refresh Token 或 Token 轮换机制
- 不做复杂角色权限系统
- 不做管理后台
- 不做组织、多租户或团队空间

**完成标准**

- 用户可以注册、登录并获取当前用户信息
- 密码以哈希形式保存
- 未登录用户不能访问需要身份的 Session、Message 和 WebSocket 能力
- 创建会话时前端不再传 `owner_id`
- 会话列表只返回当前登录用户的数据
- 消息历史和 WebSocket 只允许访问当前登录用户拥有的会话
- 两个不同用户之间的会话和消息互不可见

---

### P2-2 完整 IM 核心能力集

**目标**

把聊天产品该有的高频核心体验补齐，但不试图一次性覆盖 proposal 里的所有 IM 细节。

**要做什么**

- 会话置顶
- 会话归档
- 会话搜索
- 多会话并行切换与状态保持
- 回复消息
- 引用消息
- 重新生成
- 展开预览

**完成标准**

- 系统已不只是“能聊天”，而是具备核心 IM 产品体验
- 用户可以在多个会话之间切换，并保持各自历史、状态和任务上下文
- 回复、引用、重新生成和展开预览等核心消息操作可用

---

### P2-3 多 Provider 接入

**目标**

让系统从“只有一个真实 Agent”升级为“至少能接入两个真实 Agent 来源”的平台基础形态。

**要做什么**

- 抽象统一 Provider 适配器接口
- 至少接入两个真实 Provider
- 让后续 Orchestrator 可以基于统一 Provider 接口选择 Agent 来源

**约束**

- 这一阶段不开放用户自建 Agent
- 不要求 Provider 能力完全一致，只要求统一接入与可调用

**完成标准**

- 同一系统内至少有两个真实 Provider 可用
- 后续协作链路不依赖某个单一 Provider 的硬编码路径

---

### P2-4 多角色 Agent 元信息与基础展示

**目标**

让聊天流里出现明确的多角色协作感，而不是只有一个模糊的“机器人”。

**要做什么**

- 定义 PM、Planner、Coder、Reviewer 等固定角色
- 每个角色至少有 `name`、`role`、`avatar` 占位、`system_prompt` 基础信息
- 前端消息气泡要能展示不同角色身份
- typing 状态要能带角色名出现

**完成标准**

- 前端可以清楚区分不同 Agent 的消息身份
- 后端可以按角色组织后续协作和分派

---

### P2-5 基础动态分派的 Orchestrator

**目标**

从单 Agent 对话升级到基础多 Agent 协作，但仍控制在规则驱动范围内。

**要做什么**

- 根据用户输入决定唤起哪些 Agent
- 决定基础回复顺序
- 聚合多个 Agent 产出
- 保留规则驱动实现，不追求并行调度和复杂恢复

**约束**

- 不做并行调度
- 不做失败重试与冲突处理
- 不做高级智能编排

**完成标准**

- 系统不再只能跑单 Agent 链路
- 已具备基础动态分派能力
- 一条用户需求可以触发一轮最小多 Agent 协作

---

### P2-6 基础参与者管理群聊

**目标**

让群聊不再只是协议占位，而是具备最小可管理的协作会话能力。

**要做什么**

- 引入群聊参与者记录
- 支持群聊中的 Agent 列表展示
- 支持会话级参与者管理
- 用户可以在消息中显式 `@某个 Agent`
- 多个 Agent 能在同一会话中更稳定协作

**完成标准**

- 群聊具备基础参与者管理能力
- 用户能明确感知这是一个多角色协作会话

---

### P2-7 Diff 展示与确认意图

**目标**

让系统从聊天工具升级为“能在聊天里展示结构化产物”的多 Agent 产品，但先不进入正式状态闭环。

**要做什么**

- Coder 输出结构化代码结果
- 前端把结果显示成 Diff 卡片、结构化代码块或等价形式
- Reviewer 可围绕该产物给出审查意见
- 用户可以表达接受 / 拒绝意图

**约束**

- 这一阶段只要求“展示 + 确认意图”
- 不要求正式 Accept / Reject 改变文件状态
- 不要求 VFS 承担已确认代码状态

**完成标准**

- 聊天流中可稳定出现一类结构化代码产物
- 用户能看懂这是“待确认的代码结果”
- 用户可以表达接受 / 拒绝意图，但系统不在本阶段正式落盘

---

### P2-8 P2 联调验收

**联调要覆盖的场景**

- 注册用户
- 登录用户
- 刷新页面后恢复登录态
- 会话搜索、置顶、归档、多会话并行切换
- 回复、引用、重新生成、展开预览
- 两个真实 Provider 调用
- 多角色展示
- 基础动态分派
- 群聊参与者协作
- Diff 展示与确认意图
- 使用另一个用户登录，确认不能看到前一个用户的会话和消息

**P2 最终验收标准**

- Auth 最小正式闭环成立
- 用户数据隔离成立
- 核心 IM 体验成立
- 至少两个真实 Provider 成立
- 多 Agent 基础协作与群聊能力成立
- Diff 展示与确认意图成立

## 7. P3

### P3-1 自建 Agent

**目标**

让平台从“接入多个外部 Agent”升级为“允许用户创建自己的 Agent”。

**要做什么**

- 支持创建基础自定义 Agent
- 支持配置名称、角色、Prompt、模型、能力标签
- 让自建 Agent 可以进入会话和协作链路

**完成标准**

- 用户可创建并使用基础自建 Agent
- 平台不再只依赖内置角色和固定 Provider

---

### P3-2 Diff 操作闭环与 VFS 接入

**目标**

让 Diff 从“展示结果”升级到“可真实改变项目状态”。

**要做什么**

- 支持用户 Accept Diff
- 支持用户 Reject Diff
- 支持用户一键应用 Diff
- Reject 后重新生成
- Accept 后更新正式项目文件状态
- 引入正式 VFS 承载已确认代码状态
- 必要时把确认后的文件状态同步到磁盘或预览环境

**完成标准**

- 用户对 Diff 的操作能真实改变项目状态
- `VFS` 能反映已确认结果

---

### P3-3 完整部署发布

**目标**

把部署发布能力作为完整主线落地，而不是再拆“基础版”和“增强版”。

**要做什么**

- 生成预览 URL
- 支持静态部署
- 支持源码打包下载
- 支持容器化部署
- 在聊天流中展示部署状态卡片
- 补齐发布记录、失败反馈和恢复或重试路径

**完成标准**

- 系统具备完整部署发布链路
- 用户可以从聊天流感知预览、发布、失败反馈和恢复信息

---

### P3-4 高级调度与高级群聊

**目标**

把编排能力从基础规则升级到更强协同。

**要做什么**

- 并行调度
- 失败重试
- 冲突处理
- 多 Agent 接力协同
- 主 Agent 汇总和总结

**完成标准**

- 高级群聊与复杂协作路径可稳定演示

---

### P3-5 长期上下文与记忆

**目标**

让上下文不再局限于当前会话即时历史。

**要做什么**

- 长期记忆
- 历史摘要
- 重要信息提取
- 跨轮上下文压缩

**完成标准**

- 长会话和跨轮次协作体验明显增强

---

### P3-6 产物编辑增强

**目标**

让产物不只可展示和确认，还能被更直接地编辑和局部修改。

**要做什么**

- 更强 Diff 视图
- 全屏预览
- 对话式局部修改
- 文档、网页、代码等更完整编辑体验

**完成标准**

- 用户能围绕产物本身持续编辑，而不是只能重新发一轮大请求

---

### P3-7 P3 完整演示链路验收

**联调要覆盖的场景**

- 自建 Agent 使用
- Diff Accept / Reject / 一键应用闭环
- `VFS` 更新结果可感知
- 预览与完整部署发布
- 多 Agent 复杂协同
- 长期上下文承接
- 产物局部修改
- 发布失败反馈与恢复

**P3 最终验收标准**

- 系统具备完整产品化亮点和答辩展示张力
- 前面后移的正式闭环能力已全部补齐

## 8. 如何从本文档继续拆 task

后续建议按下面的方式继续拆：

- 一级 task：直接使用本文档的步骤编号，如 `MVP-1`、`P1-2`、`P2-5`
- 二级 task：从“要做什么”里继续拆成接口、前端、后端、联调四类子任务

例如：

- `P1-1-1` 接入首个真实 Agent Provider
- `P1-2-1` 设计句段级流式消息推送
- `P1-3-1` 注入当前会话近历史
- `P2-3-1` 抽象统一 Provider 接口
- `P2-5-1` 设计基础动态分派规则
- `P2-7-1` 设计 Diff 展示卡片
- `P3-2-1` 实现 Diff Accept / Reject
- `P3-3-1` 实现完整部署状态链路

这样拆下去会比从超细总设计里拆自然很多。
