# AgentHub 产品设计文档 (PDD)

## 1. 项目定位
打造一个 IM 聊天式的多 Agent 协作开发平台。用户通过自然语言与不同职能的 AI Agent 沟通，完成从需求拆解到代码生成的全流程，并能在网页端直接预览与比对代码。

## 2. 核心 MVP 范围 (不做范围外的事情)
- ✅ 支持 WebSocket 全双工流式群聊。
- ✅ 支持 PM、Planner、Coder、Reviewer 四种基础角色编排。
- ✅ 支持前端 Monaco Editor 级的代码 Diff 对比与文件树管理。
- ✅ 降级版预览：前端集成 WebContainers 实现静态/纯前端项目的沙盒运行。

## 3. 暂不涉及的特性 (Non-Goals)
- ❌ 暂不做复杂的用户鉴权和注册登录（测试阶段写死 UserID）。
- ❌ 暂不做复杂的按量计费系统。
- ❌ 暂不做后端数据库的 Docker 容器动态拉起沙盒（后端沙盒太复杂，延后处理）。
```

  # AgentHub 系统架构与运行规范
  
  ## 1. 核心技术栈
  
  - 前端：Next.js (App Router), Zustand, Monaco Editor, TailwindCSS
  - 后端：FastAPI, LangGraph, asyncio
  - 通信：WebSocket 进行全双工实时流式通信
  
  ## 2. 核心多 Agent 协同流程 (SOP)
  
  整个系统是一个基于状态机的群聊，分为三个核心阶段：
  
  1. **需求澄清阶段**：用户发出粗糙需求，PM Agent 接管对话并反问细节，最终输出标准的 Markdown PRD。
  2. **任务拆解阶段**：Planner Agent 读取 PRD，在后台将项目拆解为 JSON 格式的任务有向无环图（DAG），并展示在前端的 Task List 中。
  3. **编码迭代阶段**：
     - Coder Agent 认领任务并编写代码。
     - Reviewer Agent 自动读取代码并审查，合格后给出 Approve，不合格打回 Coder 重写。
     - **核心安全红线**：Coder 生成的代码绝对不能直接覆盖物理文件，必须以 Diff (补丁) 形式推给前端。
  
  ## 3. 虚拟文件系统 (VFS) 交互规范
  
  - 后端在内存中维护项目的虚拟文件目录树。
  - 只有当人类用户在前端界面点击了 “Accept (接受代码)” 按钮，前端向后端发送确认指令，后端才真正更新内存中的 VFS 并落盘。
  ```

# AgentHub 多 Agent 协同流转与 Prompt 规范

## 1. 全局状态 (Graph State)
系统在流转时，必须在内存中维护以下上下文：
- `project_context`: 当前项目的全局描述（由 PM 总结）。
- `task_list`: 任务树（由 Planner 生成）。
- `vfs_snapshot`: 当前虚拟文件系统的目录树结构。

## 2. 角色定义与流转规则 (Nodes & Edges)

### [Node 1] PM Agent (产品经理)
- **触发条件**: 用户发起新需求，或需求不清晰时。
- **系统设定 (System Prompt)**: "你是一个资深产品经理。你需要通过多轮对话挖掘用户的真实需求。当需求清晰后，输出一份包含『核心功能、页面结构』的 Markdown PRD。"
- **输出终点**: 状态更新为 `phase_planning`，唤醒 Planner。

### [Node 2] Planner Agent (架构师)
- **触发条件**: PM 输出 PRD 后自动触发。
- **系统设定**: "你是一个架构师。请阅读 PRD，并结合当前 `vfs_snapshot`，将项目拆解为多个具体的技术任务。必须严格输出 JSON 格式的任务列表。"
- **输出终点**: 状态更新为 `phase_coding`，将任务推入队列，唤醒 Coder。

### [Node 3] Coder Agent (程序员)
- **触发条件**: 任务队列中有处于 `pending` 的任务。
- **系统设定**: "你是一个前端/后端开发工程师。请认领当前任务，严格只输出针对特定文件的修改代码。不要写解释性废话。"
- **输出终点**: 产出代码后，交由 Reviewer 审查。

### [Node 4] Reviewer Agent (审查员)
- **触发条件**: Coder 提交了新代码。
- **系统设定**: "你是严格的 Code Reviewer。检查代码是否实现了任务要求，是否存在语法错误。若通过则回复 [APPROVE]，若不通过则给出具体修改建议并回复 [REJECT]。"
- **输出终点**: [APPROVE] -> 等待人类验收；[REJECT] -> 打回给 Coder 重新生成。
```

# 虚拟文件系统 (Virtual File System, VFS) 设计规范

## 1. 核心理念
- **安全隔离**：AI 生成的代码在获得人类用户明确的“接受 (Accept)”指令前，绝对不允许直接写入物理硬盘。
- **内存主导**：项目的当前状态（VFS Tree）由后端内存（或 Redis）维护。

  "files": {
    "/src/index.html": { "content": "<html>...</html>", "version": 1 },
    "/src/style.css": { "content": "body { ... }", "version": 1 }
  }
}

# AgentHub 项目 AI 编程规范与全局指令

## 0. 全局准则 (Global Rules)
- **语言强制**：与我对话时，强制使用中文。代码注释和提交信息使用中文，但变量命名、函数命名、API 路径必须使用符合语义的英文。
- **架构认知**：本项目是一个全栈 Monorepo 架构。前端位于 `frontend/`，后端位于 `backend/`，公共契约位于 `shared/`。在修改跨端逻辑时，必须同时考虑两端的影响。
- **行动前置条件**：在生成任何涉及前后端通信的代码前，必须优先阅读 `shared/schemas/ws_messages.json` 和 `shared/index.ts`，严格按照定义的字段结构进行编码，禁止自行臆造字段名。
- **代码输出约束**：只输出被修改或新增的代码块，不要重复输出无需修改的上下文本。使用清晰的注释标注插入或替换的位置。

## 1. 前端开发规范 (Next.js & UI)
- **框架限制**：本项目使用 Next.js 14+ (App Router 模式)。只允许在 `frontend/src/app` 下建立页面路由。
- **类型安全 (TypeScript)**：
  - 强制使用 TypeScript，严格禁止使用 `any` 或 `@ts-ignore`。
  - 所有 WebSocket 相关的数据结构，必须从 `shared/index.ts` 导入类型。
- **样式规范 (Tailwind CSS)**：
  - 只能使用 Tailwind CSS 进行样式编写，严禁创建独立的 `.css` 或 `.scss` 文件。
  - 避免内联的 `style={{...}}`。
- **状态管理 (Zustand)**：
  - 涉及到跨组件通信（如：多 Agent 任务进度树、VFS 文件树状态）必须使用 Zustand，统一定义在 `frontend/src/store/` 下。
  - 严禁引入 Redux 或 MobX。
- **组件化与 Hook**：
  - 业务逻辑（如 WebSocket 连接管理、消息拼接）必须抽离为自定义 Hook 放在 `frontend/src/hooks/` 下。
  - 组件只负责 UI 渲染。对于 Monaco Editor 的集成，务必处理好其生命周期和卸载逻辑，防止内存泄漏。

## 2. 后端开发规范 (FastAPI & Agent)
- **异步优先**：本项目强依赖 WebSocket。所有 I/O 密集型操作、LLM API 调用必须使用 `async/await`，严禁在路由中写入阻塞事件循环的代码。
- **数据校验 (Pydantic V2)**：
  - 必须使用 Pydantic V2 处理数据验证。
  - 所有入参和出参模型定义在 `backend/app/schemas/` 目录下，并确保与 `shared/schemas/ws_messages.json` 完全对齐。
- **状态机与编排 (LangGraph)**：
  - Agent 之间的流转必须基于 LangGraph 状态机实现，节点 (Nodes) 和边 (Edges) 的定义必须清晰解耦，放在 `backend/app/agents/` 目录下。
  - 严禁将复杂的 Agent 逻辑堆砌在 FastAPI 的 `routers` 中。
- **虚拟文件系统 (VFS) 安全**：

- 如果发生编译错误或运行时异常，不要尝试给出多重猜测。首先分析报错栈的核心原因，然后给出一个最确定的修复方案。

# PRD

课题：AgentHub - 多 Agent 协作平台

---

课题背景
通过对话式交互创建网页、Workflow 等产物。本课题要求学生构建一个该业务的简化实战版：多 Agent 协作平台（AgentHub）。
平台采用 IM 聊天作为核心交互范式。用户像使用飞书/微信一样，通过新建对话、发送消息的方式与不同 AI Agent 进行交互。每个 Agent 就是一个"聊天对象"，用户可以：

- 新建对话：创建一个新的聊天会话，选择或指定要对话的 Agent（如 Claude Code、Codex、OpenCode 等）
- 多会话并行：同时开启多个对话窗口，分别与不同 Agent 交流不同任务（类似 IM 的多个聊天窗口）
- 群聊协作：在一个对话中 @ 多个 Agent，由主 Agent（Orchestrator）自动协调分工，多个 Agent 像群聊成员一样依次回复各自的产出
- 上下文连续：每个对话保持完整的聊天历史，Agent 能基于历史消息理解上下文，支持多轮迭代修改
- 产物内联：Agent 的回复不仅是文字，还可以内联展示代码 Diff、网页预览卡片、文件附件等富媒体产物，用户可直接在聊天流中预览和操作
  平台同时接入市面主流 Agent 平台（Claude Code、Codex、OpenCode 等），通过统一的适配器层屏蔽 API 差异，并支持用户自建 Agent。所有 Agent 产出（代码、网页、文档、PPT 等）支持实时预览、代码二次编辑和一键部署发布。

---

核心功能

1. IM 聊天式交互（核心体验）
   该系统支持对话列表管理，可新建、置顶、归档、搜索会话并按最近活跃排序；提供单聊和群聊两种模式，既支持与单个 Agent 一对一对话，也支持在同一会话中通过 @指定或 Orchestrator 自动分派，实现多 Agent 依次回复；消息类型丰富，涵盖文本、代码块、图片、文件附件及网页预览、Diff 视图、部署状态等卡片，同时支持回复、引用、重新生成、复制代码、一键应用 Diff、展开预览等消息操作；在上下文管理上，聊天历史会自动传递给 Agent，也支持手动 pin 关键消息作为长期上下文。
2. 主 Agent 协调器（Orchestrator）

- 在群聊模式下，自动理解用户意图，将复杂任务拆解并分派给合适的子 Agent
- 子 Agent 完成后，Orchestrator 聚合产出并在聊天流中汇报结果
- 支持并行调度、失败降级、代码冲突处理

3. 多 Agent 接入

- 统一适配器层，至少接入 2 个主流 Agent 平台（Claude Code + Codex / OpenCode）
- 支持用户自建 Agent（对话式创建，设定 System Prompt + 工具集）
- 每个 Agent 在聊天列表中显示为独立的"联系人"，有头像、名称、能力标签

4. 产物预览与编辑

- Agent 回复中内联产物预览卡片（网页 iframe、文档渲染、【P2】PPT 浏览）
- 点击卡片展开全屏预览 / 代码编辑器
- 【P2】支持 Diff 视图、版本历史、对话式局部修改（选中代码 → 在聊天中描述修改）
  【P2】5. 部署发布
- 聊天中直接发送"部署"指令，Agent 返回部署状态卡片
- 一键生成预览 URL / 静态站点部署 / 容器化部署 / 源码打包下载

---

考察要点
本次项目从多维度进行综合考察，权重与要点分布如下：AI 协作能力占 30%，重点考察沉淀出的 Spec、skill、rules 等协作规范；功能完整度占 25%，关注 IM 核心体验流畅度与多 Agent 调度的运行效果；生成效果质量占 20%，评估聊天 UI 体验与产物预览效果；代码理解度占 15%，要求能清晰解释架构选型与核心逻辑；创新与产品感占 10%，鼓励超预期功能点、体验优化及详细产品设计方案。最终交付物需包含产品设计文档、技术文档、可运行 Demo、AI 协作开发记录及 3 分钟 Demo 视频。
