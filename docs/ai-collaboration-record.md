# AgentHub AI 协作开发记录

## 1. 文档定位

本文档记录 AgentHub 项目在开发过程中如何与 AI 协作，不以聊天截图堆砌为主，而以“协作规范、协作流程、产物索引”为核心，说明项目如何把 AI 从单次辅助工具升级为可复用的研发协作者。

本文档重点回答以下问题：

- 我们如何和 AI 做需求澄清
- 我们如何把需求沉淀为 Spec
- 我们如何用 AI 拆解任务并约束输出
- 我们如何通过 Rules、Skills、Prompts 和代码结构把协作过程工程化

---

## 2. AI 协作目标与基本原则

本项目中的 AI 协作目标，并不是简单地“让 AI 帮忙写几段代码”，而是将 AI 纳入软件研发流程的多个关键环节，使其成为需求分析、方案设计、任务拆解、代码实现和规范沉淀的一部分。

在实践过程中，我们逐步形成了以下几条协作原则：

- 文档先行：先让 AI 协助澄清问题、收敛范围，再进入编码
- Spec 驱动：以规格文档作为后续任务拆解和实现的真相源
- 规则约束：不信任无约束的自由生成，必须给 AI 明确边界
- 技能复用：把有效流程沉淀为 Skill，而不是每次重复口头描述
- 结构落地：AI 协作的产物不能只停留在对话里，要落到仓库结构中
- 人在回路：关键设计决策、能力边界和最终代码质量仍由开发者把关

这些原则和当前 AI 编程的最佳实践是一致的。高质量的 AI 协作，关键不在于“一次生成多少代码”，而在于是否建立了清晰的上下文组织、约束机制和复用路径。

---

## 3. 需求澄清：如何和 AI 对齐问题定义

### 3.1 协作目标

项目最初面对的不是单一编码问题，而是一个较复杂的比赛命题：构建一个 IM 式多 Agent 协作平台，并提交产品设计文档、技术文档、AI 协作开发记录、可运行 Demo 和视频。

这类任务如果直接让 AI 开始写代码，很容易出现两个问题：

- 把产品范围无限放大，导致实现失控
- 把比赛目标误解成单纯做一个聊天页面

因此，第一步不是编码，而是和 AI 一起澄清问题定义。

### 3.2 协作方式

在需求澄清阶段，我们主要利用 AI 做三件事：

- 帮助概括项目要解决的核心问题
- 将题目要求转译成系统目标与边界
- 明确哪些内容属于“当前必须完成”，哪些属于“后续规划”

这一阶段沉淀的核心结果体现在 `openspec/specs/proposal.md` 中。该文档不是纯技术说明，而是围绕项目背景、目标能力、交付要求和评审重点建立统一叙事。

### 3.3 产物价值

通过这一步，项目的核心定义被收敛为：

- 不是“做一个模型聊天页”
- 而是“做一个以聊天为入口、以任务执行和协作为核心的多 Agent 平台”

这为后续 Spec、Task 和代码结构提供了上位约束。

---

## 4. Spec 沉淀：如何把想法变成真相源

### 4.1 为什么需要 Spec

AI 生成最常见的问题之一，是随着上下文增长不断漂移。如果没有稳定的真相源，AI 很容易：

- 自行扩 scope
- 把后续规划误写成当前能力
- 让不同回合的实现逻辑互相冲突

因此，本项目采用 Spec 驱动协作方式，把高层设计先沉淀进仓库，再让后续协作围绕 Spec 展开。

### 4.2 当前项目中的 Spec 结构

项目当前的 Spec 主要沉淀在 `openspec/specs/` 中，包括：

- `proposal.md`：定义产品愿景、核心目标、比赛场景和交付要求
- `roadmap.md`：定义阶段路线图和阶段边界
- `implementation-phases.md`：定义更细的执行版实现文档

这三层结构分别解决不同问题：

- `proposal` 回答“要做什么、为什么做”
- `roadmap` 回答“分几步做、边界在哪里”
- `implementation-phases` 回答“每一步具体落到哪些技术能力”

### 4.3 为什么这样设计

这种分层方式符合当前 AI 协作中的一种有效实践：不要让 AI 同时处理“愿景、方案、任务、代码”四个层次，而是将其拆成多个稳定层级。

这样做的效果是：

- 降低上下文混乱
- 方便在不同阶段复用相同文档
- 让 AI 在编码前先继承统一约束

## 5. Task 拆解：如何把方案变成可执行任务

### 5.1 协作目标

Spec 解决的是“方向正确”，但还不能直接指导开发实现。下一步需要把高层方案拆成可验证、可交付的任务单元。

### 5.2 当前项目中的任务沉淀方式

项目当前通过 `openspec/changes/IM/` 维护阶段性任务和变更任务，例如：

- 不同阶段的任务文件
- 编排相关任务
- 运行时修正任务
- 路线修补与决定记录

这些任务文档承担的作用，不是为了堆积管理文件，而是为了让 AI 后续在拆任务、看上下文、推进实现时有可追溯的依据。

### 5.3 Skill 化的任务拆解规范

项目当前还将任务拆解规范沉淀到了 Skill 中。` .cursor/skills/task-planning-from-spec/SKILL.md` 明确规定了：

- task 必须基于已确认 spec
- 不允许自行扩 scope
- 每个 task 必须包含目标、边界、接口、实现步骤、测试方案和验收标准

这体现了一个重要协作原则：AI 不只是“会拆任务”，而是“按固定格式和约束拆任务”。

### 5.4 这样做的意义

任务拆解如果没有规则，AI 很容易生成：

- 粒度失衡的任务
- 跨阶段混合任务
- 没有验收标准的任务

通过把拆任务方式标准化，项目把 AI 的任务规划能力转化成了更可控的工程资产。

---

## 6. Rules 约束：如何限制 AI 输出质量

### 6.1 为什么需要 Rules

AI 能力再强，也会因为上下文缺陷、环境差异或默认假设产生低质量输出。尤其在代码协作里，常见风险包括：

- 编码格式不一致
- 文件编码错误
- 平台相关问题被忽略
- 生成结果违背项目约定

因此，我们不是完全依赖提示词，而是将关键约束显式写成规则文件。

### 6.2 当前项目中的规则沉淀

项目当前可以明确举证的规则之一是 `.cursor/rules/encoding.mdc`。该规则要求：

- 所有文本文件读写统一使用 UTF-8
- 不依赖系统默认编码
- Windows 环境下必须避免 GBK/CP936 带来的乱码问题

这类规则看似基础，但在真实协作中非常重要。因为一旦 AI 在 Windows 环境里按默认编码写中文文件，后续文档、Prompt、代码注释都可能出现不可逆损坏。

### 6.3 Rules 的实践意义

从 AI 编程最佳实践角度看，Rules 的价值在于把“反复口头提醒”升级为“可复用约束”。这样 AI 在多轮协作中不会因为上下文漂移而反复犯同类错误。

## 7. Skill 复用：如何把稳定流程沉淀为可重复协作能力

### 7.1 为什么要有 Skill

单次 prompt 适合解决一次性问题，但不适合沉淀长期稳定的方法论。对于比赛项目这类持续演进的代码库，更有效的方式是把高频协作流程模板化。

### 7.2 当前项目里的 Skill 资产

在当前仓库中，AI 协作 Skill 主要沉淀在 `.cursor/skills/` 下，比较关键的包括：

- `openspec-propose`
- `task-planning-from-spec`
- `task-review-from-spec`
- `openspec-explore`
- `openspec-apply-change`
- `systematic-debugging`

这些 Skill 的价值在于，它们把某类协作过程从“靠临场发挥”变成“按流程执行”。

### 7.3 Skill 的实际作用

以 `openspec-propose` 为例，它强调先创建 proposal、design、tasks 等文档，再进入实施。以 `task-planning-from-spec` 为例，它强调从已确认 spec 出发拆后端任务，不重新定义需求。

这说明项目中的 AI 协作不只是“调用大模型回答问题”，而是开始具备过程模板、输入输出结构和工作顺序。

### 7.4 最佳实践视角

从当前 AI 工程化实践看，Skill 的本质相当于轻量工作流或专家 SOP。它降低了对单次 prompt 质量的依赖，也提升了多人协作和后续复用的稳定性。

---

## 8. Prompt 组织：如何把 AI 从开发辅助延伸到运行时能力

### 8.1 开发期 Prompt 与运行期 Prompt 的区别

本项目中的 AI 协作不只存在于开发过程，也进入了产品运行时本身。因此需要区分两种 Prompt：

- 开发期 Prompt：用于需求澄清、Spec 生成、任务拆解、规则执行
- 运行期 Prompt：用于系统中的 Agent 实际执行用户任务

### 8.2 当前项目中的运行期 Prompt 组织

运行期 Prompt 当前沉淀在：

- `backend/app/runtime/prompts.py`
- `backend/app/runtime/prompts/*.j2`

其中已经根据不同模式组织了多套模板，例如：

- chat
- code
- doc
- legal

### 8.3 为什么要模板化

运行期 Prompt 采用模板化有几个重要原因：

- 避免把提示词散落在业务代码里
- 支持不同 Agent / 模式复用
- 让 Prompt 迭代可以与 Runtime 结构解耦
- 为后续多 Agent 角色差异化提供基础

这也体现了一个更成熟的 AI 协作思路：Prompt 不应只是临时文本，而应成为可维护的系统配置资产。

## 9. 代码实现协作：如何从文档走到代码

### 9.1 协作主线

在当前项目中，AI 协作走的是一条比较清晰的链路：

`需求澄清 -> Spec 沉淀 -> Task 拆解 -> Rules 约束 -> Skill 复用 -> Prompt 组织 -> 代码实现`

这条链路的价值在于，AI 输出不会直接跳到“生成一段代码”，而是先被文档、规则和结构约束，再进入实现。

### 9.2 代码层的实际落点

当前仓库中，AI 协作成果已经分别落在不同位置：

- `openspec/specs/`：产品与阶段文档
- `openspec/changes/IM/`：任务与变更记录
- `.cursor/rules/`：协作规则
- `.cursor/skills/`：协作技能
- `backend/app/runtime/prompts/`：运行期 Prompt 模板
- `backend/app/runtime/`：单 Agent Runtime
- `backend/app/services/orchestration_*`：群聊编排与多 Agent 执行
- `backend/app/providers/`：统一大模型接入

这说明项目中“AI 协作”的产物已经进入代码库结构，而不是停留在外部聊天工具中。

### 9.3 协作中的人机分工

当前项目的人机分工大致如下：

- 人负责定义目标、把关范围、校验边界、决定取舍
- AI 负责辅助梳理文档、拆任务、补结构、生成实现草案、对齐规范

在编码层面，AI 可以高效推进样板逻辑、事件协议、模型接入、任务状态组织等部分；但最终仍由开发者确认哪些设计合理、哪些边界需要收紧、哪些能力不应夸大。

### 9.4 对当前项目的实际收益

在 AgentHub 这个项目里，AI 协作的实际收益主要体现在：

- 更快形成产品与技术主线文档
- 更系统地收敛阶段边界
- 更容易维护多 Agent、Runtime、Provider 这些复杂结构的一致性
- 能把经验沉淀成下一轮可复用的规则和 Skill

## 11. 结合当前最佳实践的总结

结合当前 AI 编程的最佳实践，可以把本项目的协作方式总结为以下几点：

- 不把 AI 当成一次性问答工具，而是纳入完整研发流程
- 不依赖长对话记忆，而是把关键上下文沉淀进仓库
- 不让 AI 自由发挥到底，而是通过 Spec、Rules、Skills 和结构边界约束其输出
- 不只关注生成代码，而是同步沉淀协作规范和运行时 Prompt 资产

这几条做法对比赛场景尤其重要。因为比赛不仅考察“有没有做出功能”，也考察“有没有沉淀出可复用的 AI 协作方法”。

---

## 12. 结论

AgentHub 项目的 AI 协作开发，并不是若干次零散对话的结果，而是一套逐步工程化的协作机制。项目通过：

- Spec 文档统一问题定义
- Task 文档组织实施路径
- Rules 控制输出质量
- Skills 复用稳定流程
- Prompt 模板进入运行时
- 代码结构承接最终实现

最终形成了一条从需求到实现、从协作到产物的完整链路。

这也是本项目希望在比赛中展示的重点之一：AI 不只是加速编码的工具，更可以成为一种可沉淀、可复用、可复盘的软件研发协作方法。
